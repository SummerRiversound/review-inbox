コーディング中も GitHub での自分の作業を見失わないための [Claude Code](https://claude.com/claude-code) の mod です。自分のレビューを待っているプルリクエスト（それぞれ開く前にわかりやすい言葉で要約します）、オープン中の自分の PR とそれに付いたレビュー、そして自分に声がかかった Issue を表示します。

![入力欄の上の帯と、ドロワーの3つのタブ（要レビュー、自分の PR、自分の Issue）](docs/images/en/overview.gif)

## クイックスタート

[GitHub CLI](https://cli.github.com/) にログインした状態（`gh auth login`）で、Claude Code のプロンプトに入力します。

```text
/plugin marketplace add https://github.com/SummerRiversound/review-inbox.git
/plugin install review-inbox@review-inbox
/review-inbox
```

最後の行でドロワーが開きます。オプションと更新方法は [インストール](#インストール) をご覧ください。

- **入力欄の上の帯** — 自分の対応が必要なものだけを数える1行です。自分のレビューを待っている PR、要対応の自分の PR、自分に割り当てられた Issue や自分がメンションされた Issue を数えます。色は、最も長く待っているレビューリクエストの待ち日数を表します（3日から黄色、14日から赤）。`開く` でドロワーが開きます。 数が減ると、一瞬だけ緑色になります。
- **ドロワー** — `/review-inbox` で開く「レビュー受信トレイ」です。タブは5つあります。「要レビュー」「自分の PR」「割り当て・メンション」は自分が対応するもの、「保存した検索」と「通知」は見て回るためのものです。ドロワーにフォーカスがあるときに 1〜5 を押すと、左から数えてその番号のタブに移ります。タブの数字はカードの件数ですが、「保存した検索」にはなく、「通知」は未読の通知だけを数えます。
- **トースト通知** — 作業中に新しい項目が届くと、短く知らせます。

画面表示と要約は9つの言語に対応しています。詳しくは [言語](#言語) をご覧ください。

## 動作要件

- Claude Code 2.1.287 以降。mod（function-hook プラグイン）に対応した最初のビルドです。2.1.292 で動作を確認しています。mod はアーリーアクセス段階のため、リリース間で API が変わる可能性があります。
- [GitHub CLI](https://cli.github.com/)（`gh`）が `PATH` 上にあり、レビュー対象のリポジトリにアクセスできるアカウントでログイン済み（`gh auth login`）であること。
- GitHub Enterprise Server の場合: Claude Code を起動する環境で `GH_HOST` を設定してください。すべての `gh` 呼び出しがそのホストに送られます。

## インストール

Claude Code セッションの入力欄で次を実行します。

```text
/plugin marketplace add https://github.com/SummerRiversound/review-inbox.git
/plugin install review-inbox@review-inbox
```

インストール画面で以下のオプションを尋ねられます。いずれも空欄またはデフォルト値のままでかまいません。

### アップデートとアンインストール

```sh
claude plugin marketplace update review-inbox
claude plugin update review-inbox@review-inbox
claude plugin uninstall review-inbox@review-inbox
```

アップデートは再起動後に反映されます。アンインストールしても mod のキャッシュフォルダ `~/.claude/plugins/data/review-inbox` は残ります。キャッシュされた一覧と要約も消すには、このフォルダを手動で削除してください。各バージョンの変更内容は [変更履歴](CHANGELOG.md) をご覧ください。

## 設定

インストール画面で設定し、後から `/config` で変更できます。変更はすぐに反映されます。

| オプション | デフォルト | 内容 |
| --- | --- | --- |
| `scope` | 空 | すべての検索（`review-requested:@me`、`author:@me`、`assignee:@me`、`mentions:@me`）に追加する GitHub の検索修飾子です。空の場合は GitHub 全体が対象です。 |
| `githubUser` | 空 | 複数のアカウントでログインしているときに使う `gh` アカウントです（`gh auth token -u <user>`）。空の場合はアクティブなアカウントを使います。 |
| `language` | `auto` | `auto`、または [言語](#言語) にあるコードのいずれかです。 |
| `refreshMinutes` | `10` | GitHub から取得し直す間隔（分）です。5、10、15、30、60 のいずれかで、すべてのセッションが1回の取得を共有します。 |
| `repoPaths` | 空 | 次の作業ボタンで、リポジトリごとに Claude が作業するフォルダです。下を参照してください。 |
| `motion` | `auto` | `off` にすると帯の数が光りません。`auto` でも、Claude Code の動きを減らす設定（`prefersReducedMotion`）がオンなら光りません。 |
| `directActions` | `off` | `on` にすると、カードから GitHub へ直接書き込むボタンが付きます。詳しくは下の「GitHub への直接操作」を参照してください。 |
| `autoReview` | `off` | `on` にすると、自分にリクエストされた PR をバックグラウンドでレビューし、投稿するまで各レビューを自分の保留中のレビューとして保持します。**トークンを目に見えて多く使います。**この値は最初の状態にすぎません。要レビュータブの一番上にある `自動レビュー` ボタンを一度押すと、その後はボタンだけがオン・オフを決めます。オンにする前に確認します。 下の「自動レビュー」を参照してください。 |
| `autoReviewPost` | `pending` | 終わったレビューをどうするかを決めます。`pending` は保留中のレビューとして残してカードから投稿し、`comment` はコメントとして投稿し、`verdict` は提案された判定（承認・変更リクエストを含む）のまま投稿します。`pending` 以外では確認なしに自分の名前で投稿されます。 |
| `autoReviewModel` | `sonnet` | レビュアーが使うモデルです。`sonnet` か `opus` で、`opus` はより深くレビューしますが費用がかかります。 |
| `autoReviewVerify` | `off` | `on` にすると、下書きを保存する前に2人目のレビュアーが指摘ごとにコードと照らし合わせます。成り立たない指摘は外し、重すぎる重要度は下げます。指摘のあるレビューはトークンが約2倍かかります。 |
| `autoReviewDaily` | `5` | 1日に開始する自動レビューの上限です。3、5、10、20、`unlimited` のいずれかです。カードの `もう一度試す` は数えません。 |
| `autoReviewSettleMinutes` | `30` | PR の最後のコミットから自動レビューを始めるまでの時間（分）です。作成者はリクエストの直後にまたプッシュすることが多いためです。0、10、30、60、120 のいずれかで、`0` ならすぐに始めます。 |
| `autoReviewSkills` | 空 | レビュアーに読み込むスキルをカンマ区切りで指定します（自分のレビュー用プレイブックなど）。空の場合は何も読み込みません。 |
| `autoReviewInstructions` | 空 | レビュアーへの自分の指示を自由に書きます（何を先に見るか、コメントの書き方など）。空の場合は何も加えません。 |
| `autoReviewLarge` | `on` | `on` にすると、50ファイルまたは変更2,000行を超える PR もレビューします。トークンをかなり多く使います。`off` にすると対象外です。 |
| `autoReviewBacklog` | `on` | `on` にすると、自動レビューをオンにする前のリクエストも、`autoReviewDaily` の範囲で1日に数件ずつレビューします。`off` にすると対象外です。 |

`scope` には、GitHub の [Issue と PR の検索](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests) で使えるものなら何でも指定できます。

```text
org:my-org
org:my-org org:other-org
repo:owner/name repo:owner/other
org:my-org -repo:my-org/noisy-repo
user:my-username
```

`org:`、`repo:`、`user:` の修飾子を複数指定すると、そのいずれかに一致するものが対象になります。チームへのレビューリクエストも、GitHub の `review-requested:@me` の定義どおり、自分へのリクエストとして数えます。

`repoPaths` には `owner/repo=パス` をカンマ区切りで書きます。`owner/*=パス/*` はその owner のすべてのリポジトリに当てはまり、パスの `*` はリポジトリ名になります。完全な名前がワイルドカードより優先され、`~` はホームフォルダです。ここで指定したフォルダは、セッション自身のフォルダや mod が覚えたフォルダより優先されます。

```text
my-org/*=~/code/*
my-org/legacy=~/old/legacy-app
```

## タブ

各タブはカードを種類ごとにまとめて表示します。種類の見出しを押すと折りたたまれ、もう一度押すと開きます。タブ上部の `非表示 N · すべて表示` は、そのタブで非表示にしたカードだけを元に戻します。

カードの `▸ 操作` にある `メモ` で、タイトルの上に一行を残せます。何を確認したか、いつ何をすることにしたかを書いておくためのものです。`保存` するとカードは表示されたままです。`明日まで延期` と `来週まで延期` は、明日または来週月曜の午前9時までカードを隠し、それより前に新しい動きがあればすぐに戻します。新しい動きとは、レビュー依頼の PR への新しいコミット、自分の PR の状態の変化や新しいレビュー、Issue の新しいアクティビティです。延期したカードが戻るとメモ付きでトーストを表示します。`消去` でメモを消します。

上部の検索欄は、タブに関係なく全体をまとめて検索します。対象はリポジトリ、番号、タイトル、作成者、本文の先頭 2,000 文字、要約、自分のメモです。非表示や延期中のカードも `非表示` の印付きで見つかります。検索欄を空にするとタブ表示に戻ります。Claude モバイルアプリはまだ入力欄を描画しないため、モバイルではメモの表示のみで、検索と `メモ` ボタンはありません。

セッションが作業中のカードは、要レビューと自分の PR タブの先頭にある `セッションで作業中` にまとまり、そのセッションのフォルダ名か `このセッション` が表示されます。自分の PR は、あるセッションのフォルダがそのリポジトリのそのブランチをチェックアウトしているとここに入ります。どのカードも、セッションのプロンプトにその PR のリンクが入ると（`Claude にレビューを依頼` と同じように）ここに入ります。セッションが閉じられるか10分間応答がないと、カードは元のグループに戻ります。

アップデート前に開いたまま再読み込みしていないセッションのように、古いバージョンの mod を動かしているセッションがあると、一覧画面のタイトルの下に `古いバージョンのセッション 2件 (dhub2) · そのセッションで /reload-plugins を実行してください` のように表示します。そうしたセッションは一覧を別のファイルに保存するので、最新のセッションに古い一覧やエラーが混ざりません。 横の `すべて再読み込み` を押すと、キャッシュフォルダの `reload.json` を通じてそれらのセッションに依頼が届き、各セッションは手が空いたときに自分で `/reload-plugins` を実行します。そのセッションのほかのプラグインも一緒に再読み込みされます。依頼に応えられるのは 0.13.0 以降のセッションだけなので、それより古いセッションでは一度だけ直接実行してください。

このセッションのリポジトリのカードは、各グループの先頭に `このリポジトリ` の印付きで並びます。タブにほかのリポジトリも混ざっているときは、タブの上の `このリポジトリ N` と `すべて N` で、このリポジトリだけに絞ったり、すべてに戻したりできます。入力欄の上の帯は常にすべてを数えます。このセッションのリポジトリは、`gh` と同じく `GH_REPO` があればその値、なければフォルダの GitHub リモートです。

カードのタイトルの下には、ラベルを2つまで（残りは件数で）、コメント数、そして PR がリポジトリのデフォルト以外のブランチに向いているときは `→ ブランチ` を表示します。

カードのリポジトリの前に `●` が付いていれば、最後にドロワーを閉じてから更新されたカードです。GitHub の受信箱が前回の訪問以降に変わったものに印を付けるのと同じです。初めて閉じるまでは何にも印を付けません。

対応が必要なものが何もないとき（レビューリクエスト、要対応の自分の PR、自分に割り当てられた Issue やメンションされた Issue がどれもないとき）は、ドロワーのタブの上に `✓ 対応が必要なものはありません` と表示し、帯は隠れたままです。

### 要レビュー

自分のレビューを待っている PR ごとに、カードを1枚表示します。カードには1文の概要、PR の目的、影響範囲、変更規模と作成者、レビュー待ちの経過日数が載ります。スキーマ変更や必須のデプロイ順序など、リスクのある項目には ⚠️ が付きます。

- `Claude にレビューを依頼` を押すとカードが `追加済み` になり、ドロワーは開いたままなので、複数の PR を選べます。ドロワーを閉じると（Esc または ×）、追加した PR ごとのレビュー依頼が、注意点と前回の自分のレビュー以降の変更点とともに入力欄に入ります。Enter を押すまで何も送信されません。入力欄の下書きですでに依頼している PR は、ドロワーを開いたときに `追加済み` と表示されます。
- `▸ 操作` の `非表示` を押すと、その PR に新しいコミットが追加されるまでカードを隠します。
- `再リクエスト` は、レビュー済みの PR からもう一度レビューを求められたことを示します。前回の自分のレビュー以降の変更点を短くまとめて表示します。
- カードは直接リクエスト、チームへのリクエスト、ドラフトに分けて表示します。

![2枚のカードで「レビューする」を押すと「追加済み」になり、3枚目は「非表示」で隠れ、Esc で2件のレビュー依頼が入力欄に入る様子](docs/images/en/review.gif)

レビュー依頼には、普段の自分のレビュースタイルを説明する1行も付くので、Claude は自分と同じやり方でレビューします。mod は週に1回、最近レビューした PR（最大30件）に自分が残したコメントを読み、使う言語と口調、最初に見るところ、依頼の言い回しを Claude にまとめてもらいます。学習に使えるコメントが5件未満の場合、その1行を付けずに依頼します。学習に失敗した場合は前回の説明をそのまま使い、1日後に再試行します。

### 自分の PR

オープン中の自分の PR を、概要の代わりに状態とともに、対応すべき順に表示します。並び順は、変更リクエスト、CI 失敗、マージコンフリクト、レビュー待ち（古いものから）、承認済み、マージキュー内、ドラフトです。実行中の CI は状態の横に表示します。マージキューに入った PR は `マージキュー内` と表示されます。キューのチェックが通れば GitHub がマージするので、入力欄の上の帯では数えず、`マージ可能` も表示しません。

`非表示` は、PR の状態が変わるか誰かが新しくレビューするまでカードを隠します。自分のプッシュだけでは再表示されません。

![自分の PR タブ: 変更リクエストからドラフトまでの6件の PR。うち2件に新しいレビュー](docs/images/en/my-prs.png)

最新のコミットより後に提出されたレビューは、レビューした人とともに `新しいレビュー` と表示され、次にコミットするまで残ります。承認、変更リクエスト、コメントのみのレビューが対象で、スレッドへの返信も含み、人とボットのどちらからのものも数えます。却下（dismiss）されたレビューは数えません。こうした PR は要対応として数え、同じ状態の中で動きのない PR より前に並びます。モデルの呼び出しはありません。

自分が対応する番の PR（変更リクエスト、CI 失敗、コンフリクト）には、次の作業のボタンが付きます: `コメントに対応`、`CI を直す`、`コンフリクトを解消`。横には Claude が作業するフォルダを表示します。このセッションがそのリポジトリのクローンにいれば `このフォルダ`、ほかのセッションがそのリポジトリで開かれたことがあればそのフォルダ、どちらでもなければ `ローカルのクローンなし` です。ボタンは `Claude にレビューを依頼` と同じようにカードを追加します。ドロワーを閉じると、依頼文に作業内容と、コメントや失敗したログを読む `gh` コマンドが入り、そのフォルダのブランチには触れず新しい worktree で作業するよう指示します。既知のフォルダがなければ、Claude がクローンの場所を尋ねるか `gh repo clone` を提案し、あなたの返事を待ちます。GitHub の呼び出しもモデルの呼び出しも増えません。

### 割り当て・メンション

自分に割り当てられたオープンな Issue と、自分がメンションされたオープンな Issue・PR を表示します。両方に当てはまる項目は「自分に割り当て」として1回だけ表示します。その下には、過去30日間に自分の Issue や PR を参照した他の Issue・PR を、参照した人とともに表示します。自分自身による参照は除き、新しいものから20件だけを表示します。モデルの呼び出しはありません。

項目は割り当て、メンション、参照に分けて表示します。`非表示` は、その項目に新しい動きがあるまでカードを隠します。

![自分の Issue タブ: 割り当てられた Issue、メンション、他の場所からの自分の作業への参照](docs/images/en/my-issues.png)

自分に割り当てられた Issue には、同じように動く `これに取り組む` ボタンが付きます。Claude が Issue を読み、変更を計画して、新しい worktree の新しいブランチで始めます。

### 保存した検索

自分で名前を付けて保存した GitHub の検索ごとにセクションができ、件数と最近更新された 20 件を表示します。タイトルを押すと GitHub でその PR や Issue が開き、`GitHub でさらに N 件` は同じ検索を GitHub で開きます。GitHub の PR 受信箱と同じく、3 つが最初から入っています。`自分が関わる PR`（自分が参加しているが自分が作成していないオープンの PR）、`レビュー済みでまだオープンの PR`、`自分が作成したオープンの Issue` です。セクションの見出しを押すと折りたためます。検索は更新のたびに 3 つずつ実行され、失敗した検索は理由を表示するだけで、ほかの検索には影響しません。モデルは呼び出しません。

自分の保存した検索は、カードのボタンと同じ `actions.json` の `groups` に追加します。`/review-inbox add-search` を実行すると、Claude が一緒に書いてくれます。

```json
{
  "groups": [
    { "id": "team", "name": "チームの PR", "query": "org:acme is:open label:urgent", "scope": "prs", "countInBand": true },
    { "id": "reviewed-by-me", "hidden": true }
  ]
}
```

`query` は GitHub の検索構文です。`scope` は `prs` か `issues` で、検索語に種類が書かれていなければ `is:pr` か `is:issue` を付けます。検索語に `sort:` がなければ `sort:updated-desc` も付けます。`scope` 設定と `このリポジトリ` ボタンはこの検索を絞り込まないので、必要なら検索語に `org:` や `repo:` を直接書いてください。`"countInBand": true` にすると、その保存した検索の件数が入力欄の上の帯に `保存した検索 N` として加わります。組み込みの保存した検索と同じ id はそれを置き換え、`"hidden": true` は取り除きます。フィールドが欠けている項目や scope が正しくない項目は除かれ、ドロワーの一番下に警告が出て、`/review-inbox buttons` で理由を確認できます。実行するのは先頭の 15 件の保存した検索だけです。

### 通知

ほかのタブにまだ出ていない GitHub の通知を、理由ごとのセクション（`コメント`、`状態の変更`、`CI 実行` など）に分けて表示し、各セクションの中は新しい順です。セクションの見出しを押すと折りたためます。自分が作成した、または参加しているスレッドのコメント、状態の変更、新しい動きと、チームへのメンション、セキュリティアラートが入ります。自分が実行した GitHub Actions のワークフローが終わった通知も `CI 実行` として入り、押すとそのリポジトリの Actions ページが開きます。GitHub は、設定の Notifications → System → Actions で GitHub での通知をオンにしている間だけこの通知を送ります。レビュー依頼、割り当て、メンションは除き、PR や Issue がすでにカードになっているスレッドも除きます。未読のスレッドには `●` が付き、タブの数字は未読の件数です。直近30日の通知を最大100件読みます。

`完了` と `購読解除` を押すとその行はすぐに消え、10秒間 `完了しました · 元に戻す` または `購読を解除しました · 元に戻す` が代わりに表示されます。10秒たつ前にドロワーを閉じると、その時点で送ります。`完了` は GitHub の受信箱と同じくスレッドを完了にし、`購読解除` はさらに、誰かに自分がメンションされるか自分がコメントするまで、そのスレッドの通知を止めます。完了にしたスレッドは、新しい動きがあると再び表示されます。失敗するとその行が理由とともに戻ります。モデルは呼び出しません。

GitHub が通知を渡すのは gh のサインインとクラシックトークンだけです。権限がないときは、タブにそのことと手順（`gh auth login` または `gh auth refresh -s notifications`）が表示されます。

### トースト通知

新しいレビューリクエスト、自分の PR への新しいレビュー、自分の PR が変更リクエスト・CI 失敗・マージコンフリクトの状態になったとき、そして新しい割り当て・メンション・参照があったときに通知します。新しいセッションでは1件ずつ通知せず、前回いずれかのセッションが見てから変わったことを `離れている間に · CI 失敗 2` のように1回にまとめて知らせます。何も変わっていなければ何も表示しません。同時に複数届いた場合は、4.5秒間隔で1件ずつ表示します。

自分の PR が承認され、実行中の CI がなくなると、`マージ可能` を1回知らせます。

![入力欄の下に3つのトースト通知が順に表示される様子: 新しいレビューリクエスト、自分の PR への変更リクエスト、新しいメンション](docs/images/en/toasts.gif)

### カードのボタン

カードの `▸ 操作` を押すと、`メモ` と `非表示`、そして用意された依頼と一緒にカードを Claude に渡すボタンの列が開きます。レビューリクエストには `リスクを要約`、`差分を説明`、`承認コメントの下書き`、自分の PR には `レビュアーへの返信の下書き`、`CI の失敗を調査` があります。ボタンは `Claude にレビューを依頼` と同じようにカードを追加し、ドロワーを閉じると依頼が入力欄に入ります。Enter を押すまで、何も実行も投稿もされません。

キャッシュフォルダの `actions.json` に自分のボタンを追加できます。`/review-inbox buttons` がファイルのパスと中身、除かれた項目を表示し、`/review-inbox add-button` を実行すると Claude が一緒にボタンを作ります。

```json
{
  "buttons": [
    { "id": "test-plan", "name": "テスト計画", "scope": "review", "prompt": "{{.RepoPath}} で {{.PrUrl}} のテスト計画を書いて。" },
    { "id": "draft-approval", "scope": "review", "hidden": true }
  ]
}
```

`scope` は `review`、`pr`、`issue` のいずれかです。prompt では `RepoName`, `RepoPath`, `PrNumber`, `PrUrl`, `PrTitle`, `Author`, `HeadRefName`, `BaseRefName`, `IssueNumber`, `IssueTitle`, `IssueUrl` を gh-dash と同じく `{{.Name}}`, `{{Name}}`, `{{ .Name }}` の形で使え、カードに値がない変数は空になります。組み込みのボタンと同じ id にするとそのボタンを置き換え、`"hidden": true` で消せます。フィールドが欠けている、または scope や変数名が不明な項目は除かれ、ドロワーの一番下に警告が出て、`/review-inbox buttons` で理由を確認できます。ほかのボタンはそのまま動きます。`PrTitle` と `Author` は GitHub に書かれたままなので、これらを使う prompt は他人の書いた文章を Claude に渡すことになります。

### GitHub への直接操作

`directActions` を `on` にすると、カードに GitHub へ直接書き込むボタンが加わります。書き込みは自分の `gh` アカウントで行われます。

- レビュー依頼には `承認`、自分のドラフト PR には `レビュー準備完了`、ベースブランチが先に進んだ自分の PR には `ブランチを更新` が付きます。ほかの人に見えて取り消せない操作なので、最初に押すとボタンの行が、何をどのアカウントで送るかを書いた行に変わります。例: `承認: o/r#5 "Fix login"、kim として — (コメントなし)`。`承認を確定` を押すか、ドロワーがキー入力を受けている間に `y` を押すと送信します。`キャンセル` を押すか 10 秒たつとボタンに戻ります。フォーカスは `キャンセル` に移り、最初に押してから 300ms 以内の確定は無視するので、Enter を押しっぱなしにしても送信されません。
- 承認はコメントなしで、自分が見たコミットを指定して送ります。その後に新しいコミットがあれば送らず、カードにそう表示します。`ブランチを更新` はベースブランチをマージし、rebase はしません。
- チェックが失敗している自分の PR の `失敗した CI を再実行` は、最新コミットの GitHub Actions の実行のうち失敗したジョブを再実行します。自分がメンションされたイシューの `自分に割り当て` はすぐに送り、10 秒間 `元に戻す` を表示します。
- 失敗した書き込みは GitHub のメッセージとともにカードに残り、ボタンが戻ります。

マージは直接行いません。承認済みで実行中のチェックがない自分の PR には、`directActions` がオフでも `マージ` ボタンが付きます。押すと、リポジトリのマージ方法を確認して `gh pr merge` を実行する依頼がプロンプトに入り、Enter で送ると Claude Code が実行の許可を求めます。

### 自動レビュー

`autoReview` を `on` にすると、自分に直接レビューが依頼された PR を Claude がバックグラウンドで読むので、カードを開いたときにはレビューができあがっています。ボタンを押すまで作成者に見えるのは、レビューの実行中に PR に付ける自分の 👀 リアクションだけです。これは `autoReviewPost` が既定の `pending` のときです。

> **トークンを目に見えて多く使います。** レビューのたびにサブエージェントが差分とコードを読み、自分の CLAUDE.md、フック、`autoReviewSkills` のスキルを使います。1つの PR で数万トークンかかり、`opus` ではさらに増えます。カードには各レビューの費用が表示され、`autoReviewDaily` が1日に開始する数を制限します。

- **開始の条件。** 自分に直接（チームではなく）出されたリクエストで、ドラフトではなくボットが作成したものでもない PR が対象で、最後のコミットの時刻から `autoReviewSettleMinutes`（既定は30分）たつと始まります。自分のセッション全体で、同時に実行するレビューは1つです。この 👀 を見た自分の別のマシンは、その PR を飛ばします。レビューの途中で止まったマシンが残した 👀 は、1時間たつと別のマシンが引き継ぎます。オンにする前のリクエストと、50ファイルまたは変更2,000行を超える PR もレビューします。`autoReviewBacklog` または `autoReviewLarge` を `off` にすると対象外です。要レビュータブの一番上にある `自動レビュー` ボタンは、すべてのセッションで自動レビューをオン・オフします。その後 `/config` で `autoReview` を変えると、そちらが優先されます。対象がないときは何も実行せず、モデルの呼び出しもエージェントの起動もありません。
- **設定の手伝い。** 要レビュータブの `自動レビュー` ボタンで初めてオンにすると、オン・オフ（ボタンが決める）を除く自動レビューの設定ごとの役割、指定できる値、既定値、今の値をまとめた依頼が入力欄に入ります。Enter を押すと Claude が一つずつ一緒に決め、選んだ値を `/config` が保存する場所に書きます。変えた値は次のセッションから効きます。同じ依頼は `/review-inbox auto-review-config` でいつでも入れられます。
- **レビューを実行するセッション。** `自動レビュー` ボタンをオンにしたセッションが、このマシンのレビューを始めます。オンにする前の確認でもそう伝えます。別のセッションに移すにはそこで `/review-inbox auto-review-here` を、どのセッションでも始められるようにするには `/review-inbox auto-review-anywhere` を実行します。そのセッションが閉じている間、待機中の PR は待ち、カードにそう表示されます。
- **読むもの。** レビュアーが使えるのは読み取り専用のツール（`Read`、`Grep`、`Glob`）だけで、シェルは使えません。mod は PR の差分を実行フォルダに書き出し、再リクエストでは前回の自分のレビュー以降の差分も書き出します。そのリポジトリのフォルダ（次の作業ボタンが使うフォルダ）がわかっている場合は、そこに head コミットを detached worktree としてチェックアウトし、レビューを保存するときに削除します。
- **書き込むもの。** 結果は自分だけに見える**保留中のレビュー**として GitHub に書き込みます。コメントは対象の行に付け、差分の外にあるものは重大度ごとにまとめてレビューの本文に入れます。重大度の名前は mod の言語で書きます。カードには、提案された判定、重大度別の指摘、上位3件、費用が表示されます。 こうしたカードは `自動レビュー` ボタンのすぐ下の `自動レビュー完了` グループに集まります。その行の `すべて確認` を押すと元の依頼のグループに戻り、保留中のレビューはカードにそのまま残ります。その PR をもう一度自動レビューすると、また集まります。 `autoReviewPost` が `comment` か `verdict` なら保存してすぐ投稿し、その PR は要レビュータブから外れます。GitHub が投稿を拒んだ場合は保留中のレビューとしてカードに残ります。
- **投稿。** `コメントとして投稿`、`投稿して承認`、`投稿して変更を依頼` のうち、提案された判定のボタンは色付きで表示されます。`GitHub への直接操作` と同じようにカード上で確認を求めたうえで、保留中のレビューを提出します。`GitHub で開く` は PR のファイル画面を開くので、先に自分で編集できます。`セッションで仕上げる` は `Claude にレビューを依頼` の代わりに表示され、そのレビューを一緒に仕上げるよう Claude に依頼します。提出するのは、どの判定にするか自分が伝えてからです。`破棄` はレビューを削除します。これらは `directActions` がオフでも表示されます。
- **新しいコミット。** 実行中のレビューは、PR に新しいコミットが追加されたとき、クローズまたはマージされたとき、自分へのリクエストがなくなったときに止まります。内容が変わらない rebase の場合は、Claude に頼まずに、自分の編集を含む保留中のレビューを新しいコミットへ移します。それ以外の新しいコミットでは、保留中のレビューは元のコミットに残り、カードに「今投稿すると消えたコードのレビューになる」と表示して `もう一度レビュー` を案内します。カードを描画した後に PR が動いていた場合、投稿は拒否されます。
- **失敗。** 読み取れない回答や、レビュアーが diff を読めなかった場合は1回だけやり直し、それでもだめならカードが理由と `もう一度試す` を表示します。タスク一覧から止めたレビューは `もう一度試す` を待ちます。セッションが閉じられたレビューは、キューの先頭からやり直します。

## 言語

帯、ドロワー、トースト通知、入力欄に入るレビュー依頼、そしてモデルが書く要約とレビュースタイルの説明は、すべて同じ1つの言語で表示されます。

| コード | 言語 |
| --- | --- |
| `en` | 英語（English） |
| `ko` | 韓国語（한국어） |
| `ja` | 日本語 |
| `zh-CN` | 簡体字中国語（简体中文） |
| `zh-TW` | 繁体字中国語（繁體中文） |
| `es` | スペイン語（Español） |
| `pt-BR` | ブラジルポルトガル語（Português do Brasil） |
| `de` | ドイツ語（Deutsch） |
| `fr` | フランス語（Français） |

- コードを指定すると、その言語になります。
- `auto`（デフォルト）は、Claude Code 自体の `language` 設定がこれらの言語のいずれかを指していれば、それに従います。コード、英語名、その言語自身での名前のいずれでも認識します（`ja-JP`、`Japanese`、`日本語`）。そうでなければシステムのロケール（`LC_ALL`、`LC_MESSAGES`、`LANG` の順）に従い、それもなければ英語になります。中国語は、台湾・香港・マカオまたは繁体字の指定（`zh-TW`、`zh-Hant`、`繁體中文`）がない限り簡体字として扱い、ポルトガル語はブラジルポルトガル語として扱います。

要約とレビュースタイルの説明は言語ごとにキャッシュされるため、言語を切り替えると、それぞれの要約とその説明を新しい言語でもう一度作成します。上記以外の言語は英語にフォールバックします。

英語と韓国語以外の言語は Claude で翻訳したもので、まだネイティブスピーカーによる確認を受けていません。この README も同じ方法で翻訳しています。修正は Issue またはプルリクエストで歓迎します。各言語は [`hooks/locales/`](hooks/locales/) 内の1ファイルで、他のすべての言語の基準となる英語の表は [`hooks/i18n.ts`](hooks/i18n.ts) にあります。

## 読み取るものと実行するもの

この mod は、自分の `gh` を通してのみ GitHub にアクセスします。要約を作成するために PR のテキストを、レビュースタイルを説明するために週に1回自分のレビューコメントを Claude に送り、ファイルは自身のキャッシュフォルダにのみ書き込みます。以下は、mod がアクセスするものとその理由の一覧で、`claude plugin validate .` がこの mod について表示する内容と一致します。`autoReview` が `on` のときは、さらに Claude に PR のレビューを依頼し、各レビューを自分の保留中のレビューとして GitHub に保存し、レビューの実行中はそのリポジトリのフォルダに worktree を追加します。

[![reach](https://raw.githubusercontent.com/karanb192/awesome-claude-code-mods/main/badges/SummerRiversound--review-inbox--review-inbox-reach.svg)](https://mods.aidojo.si/#SummerRiversound--review-inbox--review-inbox)

- **`gh` の実行**: 一覧の取得と、週に1回の最近のレビューコメントの取得に `gh api graphql` を、再リクエストされた PR には `gh api repos/<owner>/<repo>/compare/<from>...<to>` を、`githubUser` が設定されている場合は `gh auth token -u <githubUser>` を実行します。通知タブには `gh api notifications` を、`完了` や `購読解除` を押したときは `gh api -X DELETE notifications/threads/<id>`（購読解除ではその前に `/subscription` も）を実行します。`directActions` が `on` のときにボタンを押すと、アカウント名のために `gh api user`、最新コミットの確認のために `gh api repos/<owner>/<repo>/pulls/<n>` を実行し、続けて `gh api -X POST …/pulls/<n>/reviews`（`event=APPROVE`、`commit_id`）、`gh pr ready`、`gh api -X PUT …/pulls/<n>/update-branch`、`gh api …/actions/runs?head_sha=<sha>&status=failure` と `gh api -X POST …/actions/runs/<id>/rerun-failed-jobs`、または `gh api -X POST`/`-X DELETE …/issues/<n>/assignees` のいずれかを実行します。`autoReview` が `on` のときは、各レビューの前後に `gh api …/pulls/<n>/reviews` と `…/pulls/<n>/files` を、さらに `gh pr diff` を実行し、自分の保留中のレビューとして保存するために、レビューを標準入力で渡して `gh api -X POST …/pulls/<n>/reviews` を実行します。新しいコミットへ移すときは、`…/reviews/<id>` と `…/reviews/<id>/comments` を読み、`gh api -X DELETE …/reviews/<id>` を実行してから作り直します。レビューの前後に `gh api -i -X POST …/issues/<n>/reactions`（`content=eyes`）と `gh api -X DELETE …/issues/<n>/reactions/<id>` でその 👀 を付けて外します。カードのボタンは、head コミットを確認した後に `gh api -X POST …/reviews/<id>/events`（`event=COMMENT`、`APPROVE`、`REQUEST_CHANGES`）または `gh api -X DELETE …/reviews/<id>` を実行します。mod 自身がこれ以外のネットワーク呼び出しを行うことはありません。 `autoReviewPost` が `comment` か `verdict` なら、保存したレビューに続けて `gh api -X POST …/reviews/<id>/events`（`event=COMMENT`、`APPROVE` または `REQUEST_CHANGES`）を実行します。
- **`git` の実行**: 30秒ごとにセッションのフォルダで `git branch --show-current` と `git remote -v` を実行して自分の PR のブランチにいるセッションを探し、`git rev-parse --path-format=absolute --git-common-dir` でそのリポジトリの元のフォルダを覚えます。`autoReview` が `on` でリポジトリのフォルダがわかっているときは、レビューごとにそこで `git fetch origin pull/<n>/head` と `git worktree add --detach` を実行し、レビューが終わると `git worktree remove --force` を実行します。
- **Claude への依頼**（`sonnet` モデル）: 要約ごとに、PR のリポジトリ名、タイトル、説明（先頭12,000文字）、変更されたファイルのパス（最大80件）、変更規模を送ります。再リクエストされた PR では、前回の自分のレビュー以降の各コミットメッセージの1行目と、最大60件のファイルパスも送ります。これは Claude Code の使用量に含まれます。各 PR の要約は head コミットと言語の組み合わせごとに1回作成し、要約に失敗した場合の試行はコミットごとに最大3回までです。また週に1回、レビュースタイルを説明するために、最近レビューした PR（最大30件）に自分が残したレビューコメントを送ります。コメントはそれぞれ500文字で切り詰め、最大60件、合計12,000文字までです。5件未満の場合は何も送りません。
- **サブエージェントの起動**: `autoReview` が `on` のときだけです。`auto-reviewer` を一度に1つ、`autoReviewModel` のモデルで、読み取り専用のツール、自分の CLAUDE.md、フック、`autoReviewSkills` を使って動かします。Claude Code の使用量に含まれます。このエージェントの種類は、自分の Claude が選ぶ候補の一覧には含まれません。止めるときは `TaskStop` を使います。
- **ファイルの書き込み**: キャッシュフォルダ `~/.claude/plugins/data/review-inbox` の中にのみ書き込みます（`CLAUDE_CONFIG_DIR` が設定されている場合は `~/.claude` の代わりにそれを使います）。`inbox-<hash>-f<n>.json` には一覧と要約、`hidden-<hash>.json` には非表示にした PR、`notes-<hash>.json` にはメモと延期（言語に関係なくアカウントとスコープごとに1ファイル）、`sessions.json` には生きている各セッションのフォルダ名、mod のバージョン、ブランチ、GitHub リモート、プロンプトに入った PR リンク（アカウントに関係なく1ファイル）、 `repos.json` にはセッションが開かれた GitHub リポジトリごとの元のフォルダ（次の作業ボタンが表示するフォルダ）、 `style-<hash>.json` にはレビュースタイルの説明を保存します。各ファイルは隣に一時ファイルとして書いてから `mv` で置き換えるため、書きかけのファイルを他のセッションが読むことはありません。Windows のように `mv` がない環境では、その場で直接書き込みます。自分で作った `actions.json` があればそこから読むだけで、書き込みはしません。`autoreview-<hash>.json` には各 PR の自動レビューでの状況と直近の結果を、`runs/` には実行フォルダを保存します。実行フォルダはレビューが終わると `rm -rf` で削除します。
- **環境変数の読み取り**: そのフォルダを見つけるために `CLAUDE_CONFIG_DIR`、`HOME`、`USERPROFILE` を、`gh` と同じくこのセッションのリポジトリを知るために `GH_REPO` を読みます。`LC_ALL`、`LC_MESSAGES`、`LANG` は `language` が `auto` のときだけ読みます。環境変数を設定することはありません。
- **Claude Code の設定の読み取り**: `language` が `auto` のときだけ `language` キーを、`motion` が `auto` のときだけ `prefersReducedMotion` キーを読みます。
- **入力欄の読み取りと入力**: ドロワーの開閉時だけ行います。ドロワーを開くときは、すでに依頼している PR に印を付けるために下書きを読み、閉じるときは、追加した PR の依頼を下書きの後ろに改行して追加します。

## 仕組み

開いているすべてのセッションが1回の取得結果を共有します。GitHub に問い合わせるのは1つのセッションだけで、その頻度は最大で10分に1回です。他のセッションは、そのセッションが保存した結果を読みます。

開いているすべての Claude Code セッションが mod を実行しますが、キャッシュファイルはアカウント・スコープ・言語の組み合わせごとに1つを共有し、非表示にした PR も同様です。各セッションは30秒ごとにこのファイルを読みます。ファイルが10分より古いことに気づき、短時間の取得権（claim）を獲得したセッションだけが GitHub を呼び出すため、10個のセッションを開いていてもリクエストは1回です。取得中のセッションは作業中に取得権を更新し続け、3分間更新されなかった取得権は他のセッションが引き継ぎます。取得に失敗した場合は最後に正常だった一覧を保持し、1分後に再試行します。ドロワーの `↻` を押すとすぐに取得します。

1回の GraphQL 検索で、自分のレビューを待っているすべての PR とカードに必要な情報を取得し、3つの検索をまとめたもう1回のリクエストで「自分の PR」と「割り当て・メンション」を埋めます。参照は、自分が作成した PR と Issue のクロスリファレンスイベントから取得します。GitHub は他の場所から参照されても項目の `updatedAt` を更新しないため、過去60日以内に更新された項目について、過去30日間の参照を1リクエストあたり50件ずつ確認します。GitHub が参照の検索を拒否した場合（クエリごとのリソース制限があります）、最後に取得した参照を保持し、他のタブは引き続き更新します。

この10分は `refreshMinutes` で変えられます。

## 制限事項

- 自分のレビューを待っている PR は、GitHub のベストマッチ順で最大100件です。他のタブでは、オープン中の自分の PR を最大100件、割り当てられた Issue を100件、メンションされた Issue を100件、最近更新された最大500件の項目からの参照を、それぞれ最新のアクティビティ順に読み込みます。 これより多い場合、件数は `100+` と表示されます。 各リストは25件ずつ（項目が軽い参照は100件ずつ）読み込み、届いたリストから順に表示し、GitHub がタイムアウトしたページは半分のサイズで再度リクエストします。そのため、PR が多いアカウントでも GitHub の時間制限に収まります。
- 保存した検索に表示されるのは最近更新された 20 件だけで、件数は GitHub が返すその検索の総数です。
- 通知タブは直近30日の通知を最大100件読み、GitHub が指定する間隔より頻繁には問い合わせません。
- 60日間更新されていない自分の項目への参照は検出されません。
- `新しいレビュー` は、PR に新しいコミットが追加されると消えます。GitHub の「Update branch」ボタンやボットによるコミットも含みます。
- レビューしたコミットが force-push で書き換えられた後は、再リクエストされた PR に「前回の自分のレビュー以降」の行が表示されません。
- レビュースタイルは、`scope` の範囲内で GitHub の検索が `reviewed-by:@me -author:@me` に対して返す PR から学習するため、自分が作成した PR に書いたコメントは含まれません。レビューの外で PR の会話に書いたコメントは含まれません。
- `失敗した CI を再実行` が再実行するのは GitHub Actions だけです。ほかの CI サービスのチェックはそのサービス側で再実行してください。複数の PR の一括承認と、コメント付きの承認はありません。
- 自動レビューは GitHub 上にある状態の PR をレビューします。テストやビルドは実行しません。移したレビューは、すべてのファイルのパッチが同じ場合にだけ新しいコミットへ移るので、同じファイルが変わったベースへの rebase は、もう一度レビューします。
- `autoReviewDaily` で保留になったレビューは、新しいコミットへ移す処理も一緒に保留されます。`rm -rf` は POSIX 専用なので、WSL なしの Windows では実行フォルダがキャッシュフォルダに残ります。

## トラブルシューティング

- **ドロワーに `gh` のエラーが表示される。** `gh auth status` を実行してください。複数のアカウントでログインしている場合は `githubUser` を設定してください。mod は1分ごとに再試行します。
- **帯が表示されない。** 帯は自分の対応が必要なものがあるときだけ表示されます。0件の項目は表示されません。
- **期待した言語で表示されない。** `/config` で `language` を `auto` ではなく言語コードに設定してください。
- **その他の問題。** `claude --debug` で Claude Code を起動してください。この mod のログ行は `review-inbox:` で始まります。

## 開発

```sh
claude plugin validate .
claude plugin test .
claude --plugin-dir .
```

`claude plugin validate` と `claude plugin test` はログイン不要で、CI は動作確認済みの Claude Code ビルドでその両方を実行します。`tsconfig.json` は `.claude-plugin/types/tsconfig.json` を継承します。このファイルは Claude Code がこのフォルダから mod を初めて読み込むときに生成するもの（`.gitignore` で除外済み）なので、`tsc -p .` で型チェックする前に `claude --plugin-dir .` を一度実行してください。
